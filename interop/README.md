# Interop tests

Docker based interop tests between CORBA implementations, run by
[`.github/workflows/interop.yml`](../.github/workflows/interop.yml) on every
push and pull request. The matrix pairs every client (omniORB C++, omniORBpy,
rustorb in Rust, in Python and in C++) with every server (the same five); see
[The rustorb client and server](#the-rustorb-client-and-server),
[The rustorb Python client and server](#the-rustorb-python-client-and-server)
and [The rustorb C++ client and server](#the-rustorb-c-client-and-server).

| Path | Contents |
| --- | --- |

| `impls/omniorbpy/` | Echo server and test client on omniORBpy, the naming service check and the naming service restart check |

## Running locally

Docker with the Compose plugin is needed. The first build compiles omniORB
and omniORBpy, which takes a few minutes.

```sh
interop/run-matrix.sh --build --capture        # all pairs, with GIOP captures
interop/run-matrix.sh --capture --giop 1.1     # all pairs, clients limited to GIOP 1.1
interop/run-matrix.sh omniorbpy:omniorb-cpp    # one pair: CLIENT:SERVER
interop/run-naming-check.sh
interop/run-naming-check.sh --naming rustorb   # against rustorb-names, with a restart
interop/run-matrix.sh --naming rustorb         # all pairs, rustorb-names instead of omniNames
interop/run-matrix.sh --suite any              # Any / TypeCode suite
interop/run-matrix.sh --suite value            # valuetype suite
interop/run-matrix.sh --suite custom           # custom valuetype suite
interop/run-matrix.sh --suite abstract         # abstract interface suite
interop/run-wire-probe.sh
interop/run-poa-probe.sh
interop/run-timeout-probe.sh
interop/run-load.sh --seconds 10               # load on every server, rates in out/load.md
interop/run-dynany-probe.sh
interop/run-orb-ops-probe.sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-pymapping-check.sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-openrtm.sh
interop/scripts/golden-compare --all interop/out interop/golden
```

Logs and captures go to `interop/out/<client>-to-<server>/` (with
`-giop1.1` appended for `--giop 1.1`, `-any` for `--suite any`, `-value` for `--suite value`, `-custom` for `--suite custom` and `-abstract` for `--suite abstract`):
`client.log`, `server.log`, `naming.log`, and with `--capture`,
`capture/capture.pcap` and `capture/messages/` (one `.bin` file per GIOP
message, header included, and a `messages.json` index).

Each line of the summary is `PASS`, `XFAIL` (only failures listed in
`known-failures.txt`) or `FAIL`. A listed failure that starts passing is also
a `FAIL`, so that the list stays current.

## Topology

```
          corbaloc::naming:2809/NameService
 client ─────────────────────────────────────▶ naming (omniNames :2809)
  :2811 ◀──── callbacks ────┐                     ▲
   │                        │                     │ bind interop/Echo
   └──── Echo calls ──────▶ server :2810 ─────────┘
```

All three run in their own container on one Compose network. Every IOR
carries the host name (`naming`, `server`, `client`) and a fixed port rather
than an IP address, and the Echo and Callback objects live in PERSISTENT /
USER_ID POAs with fixed object ids (`InteropTest/Echo`,
`InteropTestClient/Callback`). Object keys and IORs are therefore the same on
every run, which is what makes the captures usable as golden files.

## The test IDL

`idl/InteropTest.idl` covers what the stage 1 plan lists: basic types,
string / wstring, struct, enum, unions (long and enum discriminators,
multiple labels, default, implicit default), sequences, arrays, typedefs,
user and system exceptions, in / out / inout, attributes, oneway, object
reference passing (including nil) and callbacks from the server to the
client. Any is left for stage 2 (M5).

The comment on each operation is its specification. Every server must
implement it exactly, and every client runs the same cases (78 at the
moment) with the same values, so that the captures from different clients
can be compared too. For example, the char string test sends `caf\xe9` in
ISO-8859-1, omniORB's native char code set, from both clients.

## Implementation contract

`impls/<name>/server` and `impls/<name>/client` are executables that take:

| Option | Meaning |
| --- | --- |
| `--naming CORBALOC` | root naming context, e.g. `corbaloc::naming:2809/NameService` |
| `--name PATH` | slash separated name of the Echo object (the server creates missing contexts) |
| `--host HOST` / `--port N` | host name and fixed port to listen on and publish in IORs |
| `--timeout S` | how long to retry while the naming service or server is not up yet |
| `--shutdown-server` | (client) call `Echo::shutdown` at the end |

Other arguments are ORB options. The server prints `server ready: PATH`
once bound. The client prints `ok   <case>` or `FAIL <case>: <reason>` per
case, then `N passed, M failed`, and exits with 0 only when all cases pass.

## The rustorb client and server

`impls/rustorb/` is a Cargo package in the workspace (`rustorb-interop`).
Its stubs and skeletons for `InteropTest.idl` are written by hand until the
code generator exists (`src/idl.rs`, shared by both). The server
(`rustorb-interop-server`) serves Echo from a PERSISTENT / USER_ID POA named
`InteropTest` and binds it with the `rustorb-naming` client; the client
(`rustorb-interop-client`) resolves Echo the same way and serves its
Callback object from a POA named `InteropTestClient`, like the omniORB
clients, so it runs every case.

`run-matrix.sh` builds both with cargo on the host when rustorb is in the
run, copies the binaries to `impls/rustorb/bin/`, and the client and server
containers mount that directory (the image and the CI runner are both
Ubuntu 24.04). `CLIENT_IMPLS` and `SERVER_IMPLS` choose the clients and
servers; rustorb is in both by default.

```sh
interop/run-matrix.sh rustorb:omniorb-cpp omniorbpy:rustorb rustorb:rustorb
interop/run-matrix.sh --giop 1.1 omniorb-cpp:rustorb
```

`rustorb-naming-check` (`impls/rustorb/naming-check`) runs the operation
sequence of `impls/omniorbpy/naming_check.py` with the `rustorb-naming`
stubs and `corbaname:` URLs, and prints the same lines. The other bindings
have the same check: `impls/rustorbpy/naming_check.py` (the omniORBpy one on
the rustorb package), `impls/rustorbcpp/naming_check.cc` and
`impls/rustorbjava/probe/interop/NamingCheck.java`. `run-naming-check.sh`
compares every client with the same expected output recorded from omniORBpy
and omniNames (`--update` records it again; `--client IMPL` runs one client).
The rustorb checks bind the `test` context, not the root, as the "any
object": its IOR comes from the naming service, while the root's was made
from the corbaloc URL, and `_is_equivalent` compares IORs.

```sh
interop/run-naming-check.sh                    # all five clients
interop/run-naming-check.sh --client rustorbcpp
```

## The rustorb Python client and server

`impls/rustorbpy/` (`rustorbpy` in the matrix) holds `client.py` and
`server.py` of `impls/omniorbpy/` with `from omniORB import ...` replaced by
`from rustorb import ...`: the same cases, the same servant, the same POA
calls. That is the check of the Python binding (M3): code written for
omniORBpy runs on rustorb with only the imports changed. `build.sh`, which
`run-matrix.sh` runs on the host, builds the rustorb package with its native
module into `impls/rustorbpy/lib/` (a stable ABI extension, not linked to
libpython, so it loads in the image's Python) and generates the
`InteropTest` and `CosNaming` stubs with rustorb-idl into
`impls/rustorbpy/stubs/`; idl_parser must be importable or `IDL_PARSER_DIR`
set. The client takes `ORBmaxGIOPVersion` from the environment, as omniORB
does, for `--giop`.

```sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-matrix.sh rustorbpy:omniorbpy omniorbpy:rustorbpy
```

Without Docker, the Python client and server also run on the host against
the other implementations, for example with `rustorb-names -start 2809` and
`--host 127.0.0.1`.

## The rustorb C++ client and server

`impls/rustorbcpp/` (`rustorbcpp` in the matrix) is the check of the C++
binding (M4): the cases of the other clients (`cases.h`, same case names)
and the Echo servant (`echo_impl.h`) on the IDL to C++11 mapping, with
stubs and skeletons generated by `rustorb-idl -bc++11` and the headers in
`cpp/include`. `build.sh`, which `run-matrix.sh` runs on the host, builds
librustorb_ffi with cargo, generates the `InteropTest` and `CosNaming` code
into `impls/rustorbcpp/gen/` and links the client and the server into
`impls/rustorbcpp/bin/` (libstdc++ statically, so the binaries only need
the image's glibc); idl_parser must be importable or `IDL_PARSER_DIR` set.
The client takes `ORBmaxGIOPVersion` from the environment, as omniORB does,
for `--giop`.

```sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-matrix.sh rustorbcpp:omniorb-cpp omniorb-cpp:rustorbcpp
```

`cpp/tests/test_interop.cc` runs the same cases against the same servant in
one process (two ORBs), without Docker or a naming service.

## The Java clients and servers (rustorbjava, jacorb)

`impls/java/` holds one Java client and server, on the standard IDL to Java
mapping, for two ORBs (docs/java-binding.md): `rustorbjava`, the check of
the rustorb Java binding (M6), and `jacorb`, JacORB 3.9. The system property
`interop.orb` (set by each `client` / `server` script) picks the ORB-specific
options: the endpoint (`-ORBendPoint` for rustorb, `OAIAddr` / `OAPort` for
JacORB) and the GIOP limit (`-ORBmaxGIOPVersion`, `jacorb.giop_minor_version`,
from `ORBmaxGIOPVersion` in the environment). `impls/rustorbjava/build.sh`,
which `run-matrix.sh` runs on the host, builds librustorb_jni with cargo and
compiles the rustorb Java runtime, the stubs from `rustorb-idl -bjava` and the
shared sources into `impls/rustorbjava/classes/`; the image runs it on Java
17. The image compiles the same sources against JacORB's jars with stubs from
JacORB's IDL compiler (`impls/jacorb/idl/` has the `orb.idl` it needs).

```sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-matrix.sh rustorbjava:jacorb jacorb:rustorbjava
```

`rustorbjava-portable` compiles the same shared sources, with the stubs,
skeletons and Helpers that JacORB's IDL compiler generated in the image
(`/opt/interop/impls/jacorb/gen`), against the rustorb Java runtime instead
of JacORB's jars: generated code of another IDL compiler (portable stubs on
`ObjectImpl._request` / `_invoke`, Helpers on the stream operations of Any)
running on rustorb. `impls/rustorbjava-portable/build.sh` takes the sources
out of the image, so the image must be built first. It is not in the
default matrix; CI runs it against every implementation:

```sh
p=rustorbjava-portable; pairs="$p:$p"
for x in omniorbpy omniorb-cpp jacorb rustorb rustorbpy rustorbcpp rustorbjava; do
  pairs="$pairs $p:$x $x:$p"
done
IDL_PARSER_DIR=path/to/idl_parser interop/run-matrix.sh $pairs
```

The any suite leaves `jacorb` out by default: the anys that JacORB's
generated Helpers make do not have the TypeCodes of `AnyTest.idl` (see
docs/java-binding.md), so most cases fail on that and not on the wire. Name
the pairs to run it anyway. The same Helpers make `rustorbjava-portable` fail
the same cases, so CI leaves it out of the any suite too. The value suite runs `jacorb` too: the shared
`ValueTests.java` registers implementation classes and factories of its own
for the valuetypes (JacORB generates abstract classes and no default
factories). JacORB 3.9 cannot write a value in an any on Java 17, so the
three `echo_any` cases of its pairs are in `known-failures.txt`. `java/`
(`mvn verify`) runs the same cases in one process. For the same reason
(its `DataOutputStream.write_Value`), JacORB cannot marshal the `Blob` of
the custom suite, whose cases but the null and empty ones are in
`known-failures.txt` for its pairs. The Java client prints the stack trace
of an unexpected exception when `INTEROP_TRACE` is set.

## The rustorb naming service

`--naming rustorb` replaces omniNames with `rustorb-names` (the daemon of
`crates/rustorb-naming`), built with cargo on the host and mounted into the
naming container like the client and server. `impls/rustorb/naming-service`
starts it like `scripts/run-omninames`: on port 2809, publishing
`naming:2809`, with its data in `/tmp/rustorb-names` of the container
(`-start` only on the first start). The naming check must give the same
output as with omniNames. Then `run-naming-check.sh` saves the IOR of the
context `test`, restarts the naming container, and `naming_restart.py`
checks that the bindings and the saved IOR still work. With
`run-matrix.sh --naming rustorb`, the results go to
`<client>-to-<server>-naming-rustorb`; they are not compared with the golden
files, which hold the omniNames traffic.

Without Docker, the client also runs against omniORB built on the host, for
example `rustorb-interop-client --naming corbaloc::127.0.0.1:2809/NameService
--name interop/Echo`, with the servers started with `--host 127.0.0.1`.

## Adding an implementation

1. Add `impls/<name>/` with `server` and `client` following the contract.
2. Put it in an image: either extend `docker/omniorb/Dockerfile`, or build
   another image and point the role at it with `SERVER_IMAGE` /
   `CLIENT_IMAGE`. The client image needs `tcpdump` and the `scripts/`
   directory for `--capture`.
3. Add the name to `IMPLS` in `run-matrix.sh` (or the environment) so that
   it is paired with every other implementation.
4. To test another naming service, set `NAMING_IMAGE` and `NAMING_CMD`
   (`--naming rustorb` does this for rustorb); it must listen on
   `naming:2809` with the object key `NameService`.

## Golden files

`golden/<client>-to-<server>.json` holds every GIOP message the client sent
and received (naming service, Echo server and callbacks), in request / reply
order, with the decoded header fields and the whole message as hex. The
Fragments of a message follow it. `golden/<client>-to-<server>-giop1.1.json`
is the same run with the client limited to GIOP 1.1 (omniORB's
`ORBmaxGIOPVersion`, set through `CLIENT_MAX_GIOP` in `compose.yaml`). The CI
job captures a fresh run and compares it with these files. It ignores
request ids, the alignment padding and reserved octets in GIOP headers, the `posted` polling
(its count depends on timing) and CloseConnection messages. The oneway test
runs last for the same reason. Repeated local runs match byte for byte.

**omniORB does not clear alignment padding.** The padding bytes in headers
and bodies hold whatever was left in its buffer (for example `78 78` from
the earlier 10000-character `x` string, or `44 4c 3a` from `IDL:`). Header
padding is located by `giop-extract` (the `padding` field) and masked;
body padding is stable between runs of the same pair, so it is compared as
is. The consequence for rustorb: its encoder should write zeros, and golden
tests must mask padding (or compare decoded values) rather than expect
omniORB's bytes there. Apart from padding, the omniORB C++ and omniORBpy
clients send identical request bodies for every Echo operation.

They are the reference for the rustorb CDR / GIOP golden tests
([`crates/rustorb-giop/tests/omniorb_golden.rs`](../crates/rustorb-giop/tests/omniorb_golden.rs)):
a rustorb encoder must produce the same bytes as omniORB for the same
request, and the decoder must read omniORB's replies. When the IDL, the test cases or the
omniORB version change, regenerate them:

```sh
interop/run-matrix.sh --capture
interop/scripts/golden-compare --update --all interop/out interop/golden
```

## omniORB wire format findings

Observed on the wire only: in the captures above, and with
[`scripts/wire-probe`](scripts/wire-probe), which sends hand-built GIOP 1.2
requests to each Echo server (`run-wire-probe.sh`, results in
`expected/wire-probe-<server>.txt`). The golden tests in `rustorb-giop`
keep rustorb in line with them, and the rustorb servers of every binding
give the same answers as omniORB C++ (`expected/wire-probe-rustorb.txt`).

- **wstring sent (GIOP 1.2)**: omniORB and omniORBpy send a non-empty
  wstring as a BOM followed by UTF-16 in the stream byte order (`ff fe` and
  little-endian code units in their little-endian messages). An empty
  wstring is just a zero length, with no BOM. rustorb writes the same bytes
  by default (`Encoder::set_wstring_bom(false)` gives the big-endian form
  without a BOM).
- **wstring received (GIOP 1.2)**: both servers read a wstring without a
  BOM as big endian, whatever the stream byte order (little-endian code
  units come back as `栀攀氀氀漀`), as the specification says, and accept a
  BOM of either order. rustorb reads the same way.
- **wchar (GIOP 1.2)**: omniORB sends an octet length of 2 and the code
  unit in big endian, no BOM, whatever the stream byte order. The omniORB
  C++ server reads a length of 2 as big endian and a length of 4 as a BOM
  followed by the code unit.
- **Fragments (GIOP 1.1)**: the data in each Fragment is aligned relative
  to the start of that Fragment message, not to the joined message. omniORB
  ends every fragment but the last on an 8-byte boundary (fragments are
  8192 bytes here) and continues at offset 12 of the next one, so an
  8-byte value after a boundary is 4 bytes off if the fragments are simply
  concatenated. The `echo_records[large]` case (400 records with doubles)
  shows this in both directions. rustorb's `FragmentAssembler` keeps the
  fragment boundaries for the decoder.
- **Fragments (GIOP 1.2)**: the data starts at offset 16 of each Fragment
  and fragments end on 8-byte boundaries, so the per-fragment and the
  joined alignment agree.
- **wchar / wstring over GIOP 1.1** do not work between omniORB peers (see
  `known-failures.txt`).

## Client timeout probe

`run-timeout-probe.sh` records how omniORBpy's client timeouts
(`omniORB.setClientCallTimeout` globally and per reference,
`setClientThreadCallTimeout`, `setClientConnectTimeout`) behave, and checks
rustorb's through its omniORB compatibility package
([`docs/timeouts.md`](../docs/timeouts.md)). `scripts/timeout-probe` runs a
GIOP server that never replies and a listener whose accept queue is full in
its own process, and prints for each combination of settings the exception,
which of the configured times the call took, and the GIOP messages the
server read. The two expected files differ only where rustorb chose to:
the minor code, `CancelRequest` instead of closing the connection, and no
`LocateRequest` before the first call through a `corbaloc` reference.

```sh
interop/run-timeout-probe.sh               # omniorbpy and rustorbpy
interop/run-timeout-probe.sh --update      # record expected/timeout-probe-*.txt again
```

## ORB operations probe

`run-orb-ops-probe.sh` records how omniORBpy answers the remaining standard
ORB operations, and checks rustorb's through its omniORB compatibility
package ([`docs/orb-operations.md`](../docs/orb-operations.md)):
`ORB.id`, `list_initial_services`, `register_initial_reference` (an empty
name, a name given with `-ORBInitRef`, nil, a name twice, a local object),
`create_policy` for each POA policy and with anys of the wrong type, and
whether `CORBA.Object` has the policy operations. The expected files
differ where omniORBpy has no Messaging timeout policy and no policy
operations on objects, where it accepts `RootPOA` in
`register_initial_reference`, and where it answers an any of the wrong
type with `BAD_POLICY_VALUE` instead of the `BAD_POLICY_TYPE` of the
specification.

```sh
interop/run-orb-ops-probe.sh               # omniorbpy and rustorbpy
interop/run-orb-ops-probe.sh --update      # record expected/orb-ops-probe-*.txt again
```

## POA and thread model probes

`run-poa-probe.sh` records how omniORB's POA dispatches requests, which
[`docs/poa-design.md`](../docs/poa-design.md) relies on, and checks that
rustorb's POA does the same. The probe servers
(`impls/omniorbpy/poa_probe_server.py`, `impls/omniorb-cpp/poa_probe_server.cc`,
`impls/rustorb/src/poa_probe_server.rs`, and on the rustorb C++ and Java
bindings `impls/rustorbcpp/poa_probe_server.cc` and
`impls/rustorbjava/probe/interop/PoaProbeServer.java`, built on the host like
the other rustorb programs) publish `PoaProbe::Target` objects in POAs with different policies (lifespans,
id assignment, thread models, servant managers, a default servant, an
AdapterActivator, a POA under its own POAManager) and a `Control` object
that changes their state. `scripts/poa-probe` talks to them with hand-built
GIOP only, so it can pipeline requests on one connection and send object
keys no stub would send. Each server is started three times: to record the
object keys, after a restart to see which keys survive and to run the
probe, and once more for `ORB::shutdown(false)` inside an upcall.

```sh
interop/run-poa-probe.sh                # all six servers
interop/run-poa-probe.sh omniorb-cpp
interop/run-poa-probe.sh --update       # record expected/poa-probe-*.txt again
```

The output lists derived facts (whether calls overlapped, how many threads
ran them, which exception or locate status came back) rather than timings,
so it is the same on every run. omniORB C++ and omniORBpy give identical
results; the design document summarises them. The Python, C++ and Java
servers run on the same core as the Rust one, so they are compared with
`expected/poa-probe-rustorb.txt`, which checks their servant managers and
adapter activators end to end.

## Python mapping check

`run-pymapping-check.sh` checks that the Python code of
`rustorb-idl -bpython` (see
[`docs/python-codegen.md`](../docs/python-codegen.md)) has the same public
API as the code of omniidl -bpython. `scripts/pymapping-dump` imports the
generated packages and prints what applications see: constants and their
values, enums, structs, unions and exceptions constructed and read back,
every `_tc_*` TypeCode through the standard TypeCode operations, the
interface, stub (`_objref_*`) and skeleton classes with their base classes
and the methods of the stubs. It never looks at the runtime's internals (the
operation and type descriptors of omniORBpy, for instance), so the two
outputs can be compared line by line. rustorb-idl runs on the host and needs
idl_parser (`IDL_PARSER_DIR`, or installed).

```sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-pymapping-check.sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-openrtm.sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-pymapping-check.sh --update
```

`expected/pymapping-rustorb.txt` differs from
`expected/pymapping-omniorbpy.txt` only where rustorb follows the CORBA
specification on purpose:

- the TypeCode of a local interface is `tk_local_interface` (omniORBpy:
  `tk_objref`);
- TypeCode member names are the IDL names: `global` for a member named
  `global` (omniORBpy: `_global`, the Python name);
- `CORBA.TC_Object` has the repository ID `IDL:omg.org/CORBA/Object:1.0`
  (omniORBpy: an empty ID);
- a typedef of a fixed type (`typedef fixed<5, 2> Money;`) has a class
  `Money` like every other typedef (omniORBpy makes none).

The unit tests of the generator compare the rustorb output with the
expected file too, so a change of the generated API shows up without Docker.

## OpenRTM-aist

`run-openrtm.sh` checks the omniORBpy compatibility package with real
applications. It clones OpenRTM-aist-Python, rtshell and rtctree into
`out/openrtm`, generates the stubs of their IDL with rustorb-idl on the host
and with omniidl in the omniORB image (rtctree's into a copy of rtctree,
with `-Wbpackage=rtctree.rtc`), and runs two scripts in the image, where
the examples of OpenRTM-aist (C++) are built on omniORB:

- `openrtm/scenarios.py`: for each example two RTCs, each on rustorb or
  omniORBpy (four combinations), or one in C++ and one on rustorb (both
  ways). `openrtm/connect.py` (on a Python RTC's ORB) connects their ports
  and activates them, and the output of the second RTC is checked.
- `openrtm/rtshell.py`: rtls, rtcat, rtconf, rtcon, rtact, rtdeact, rtdis
  and rtexit on the SimpleIO RTCs, and a zombie in rtls after a kill; RTCs
  on rustorb, omniORBpy or in C++ with rtshell on rustorb, and RTCs on
  rustorb with rtshell on omniORBpy.

| Scenario | Example | What goes through |
| --- | --- | --- |
| `simpleio` | `SimpleIO` (ConsoleIn to ConsoleOut) | a `TimedLong` data port (corba_cdr, push, flush) |
| `seqio` | `SeqIO` (SeqOut to SeqIn) | ten data ports of basic types and sequences |
| `simpleservice` | `SimpleService` (MyServiceConsumer calls MyServiceProvider) | a service port |

```sh
IDL_PARSER_DIR=path/to/idl_parser interop/run-openrtm.sh
interop/run-openrtm.sh --naming rustorb    # rustorb-names in place of omniNames
interop/run-openrtm.sh --only simpleio     # scenarios.py only
# Without Docker: omniidl and omniNames on the PATH; without
# OPENRTM_CXX_EXAMPLES the C++ RTCs are left out
OMNIORBPY_DIR=/path/to/site-packages PYTHON=python3.12 \
  OPENRTM_CXX_EXAMPLES=/path/to/examples interop/run-openrtm.sh --local
```

The logs of each RTC and of the rtshell commands are in
`out/openrtm/<naming>/logs`; `--log-level DEBUG` of `openrtm/scenarios.py`
adds OpenRTM-aist's own log to them. OpenRTM-aist RTCs rebind their names
in the naming service now and then, so RTCs left running from other runs
on the same naming service port take over the names; the scenarios need a
naming service of their own.

## Known issues in omniORB found by these tests

- **omniORBpy cannot unmarshal wchar** (4.3.2 and 4.3.4): on Python 3.3 and
  later, `unmarshalPyObjectWChar` in `modules/pyMarshal.cc` reads a wchar
  with `unmarshalChar()`, so a GIOP 1.2 wchar (length octet plus UTF-16)
  leaves bytes behind. The omniORBpy server closes the connection with
  "Garbage left at end of input message", and the omniORBpy client raises
  `COMM_FAILURE`. Marshalling is correct, so rustorb receiving wchar from
  omniORBpy is not affected.
- **omniORBpy's `TypeCode.member_count()` returns a float for exceptions**
  (4.3.4): `member_count()` of a `tk_except` TypeCode gives `2.0` instead of
  `2`, so `range(tc.member_count())` raises `TypeError`.
  `scripts/pymapping-dump` converts it with `int()`.
- **omniORB C++ does not convert wchar_t above U+FFFF to surrogate pairs**:
  sending `L"\U0001F980"` raises `BAD_PARAM`, and received surrogate pairs
  stay as two `wchar_t` values. The C++ client therefore sends the
  surrogate pair itself.
