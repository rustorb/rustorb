# Failures that come from the existing ORBs themselves, not from the tests.
# run-matrix.sh treats these as expected, and reports a listed case that
# starts passing so that the entry can be removed.
#
# Format: [giop=VER] CLIENT SERVER CASE REASON...   (CLIENT / SERVER may be *)
#
# A line with giop=VER applies only to `run-matrix.sh --giop VER` runs.
# The list is for the basic suite; `--suite any` has no known failures.

# omniORBpy 4.3.4 (and 4.3.2) unmarshals a GIOP 1.2 wchar with unmarshalChar()
# instead of unmarshalWChar() on Python >= 3.3 (modules/pyMarshal.cc,
# unmarshalPyObjectWChar). Marshalling is correct, so the requests and
# replies it sends are fine, but it cannot read a wchar it receives.
omniorbpy * echo_wchar[0] omniORBpy cannot unmarshal wchar replies
omniorbpy * echo_wchar[1] omniORBpy cannot unmarshal wchar replies
omniorbpy * echo_wchar[2] omniORBpy cannot unmarshal wchar replies
* omniorbpy echo_wchar[0] omniORBpy cannot unmarshal wchar requests
* omniorbpy echo_wchar[1] omniORBpy cannot unmarshal wchar requests
* omniorbpy echo_wchar[2] omniORBpy cannot unmarshal wchar requests

# wchar / wstring do not work over GIOP 1.1 between omniORB peers. The
# omniORBpy client raises BAD_PARAM_WCharTCSNotKnown before sending. The
# omniORB C++ client sends the value in the GIOP 1.2 form anyway, and both
# servers reply with BAD_PARAM minor 0x4f4d0017 (BAD_PARAM_WCharTCSNotKnown).
# The rustorb server reads the omniORB C++ client's value as GIOP 1.1 data
# (UTF-16, as negotiated in the code set context) and echoes it, and the
# client then fails to read the reply (MARSHAL). The rustorb clients and
# servers (rustorb, rustorbpy) agree on GIOP 1.1 wchar data, so those pairs
# are not listed.
giop=1.1 omniorb* * echo_wchar[0] omniORB has no GIOP 1.1 wchar code set
giop=1.1 rustorb* omniorb* echo_wchar[0] omniORB has no GIOP 1.1 wchar code set

giop=1.1 rustorb* omniorb* echo_wchar[1] omniORB has no GIOP 1.1 wchar code set
