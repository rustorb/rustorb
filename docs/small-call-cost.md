# 小さな呼び出しの残りのコスト（#207）

Nov 27, 2026 · @ysuga · [速度の改善の計画](perf-plan.md)の段 4（issue [#207](https://github.com/rustorb/rustorb/issues/207)）

段 2・3（#205・#206）で起床を減らした後の、1 回の呼び出しで ORB が使う分を削った。プロファイル（クラウドの 4 コアの仮想マシン、`perf record`、`malloc` の uprobe、`-ORBstatistics 1`）で見えたのは、次の 3 つ。

1. **クライアントは呼び出しごとに読み込みを epoll から外し、戻していた。** 返事を読んだスレッドは読み込みをタスクに返す（`release`）。そのたびに先読み（`recv`、たいてい `EAGAIN`）とポーラーへの登録（`epoll_ctl` と tokio の登録の確保）をし、次の呼び出しの `claim` でまた外していた。外した登録の片づけで I/O スレッドも起きていた（`eventfd_write`）
2. **待つ前に読んでいた。** 要求を送った直後に `recv` しても返事はまだなく、`EAGAIN` の後で `poll` していた
3. **確保が多い。** クライアントは ping 1 回で `malloc` が 24 回。半分は IOR のプロファイルの解析（`TaggedProfile::iiop`、コンポーネントとコードセットの情報）を呼び出しごとにしていたため。ほかに、コードセットの文脈の組み立て（2 回）、要求ヘッダのための操作名・オブジェクトキーの複製、接続の検索のキー（`host.to_owned()`）、使わない例外（`SystemException` は名前を `String` で持つ）。サーバーは 13 回で、オブジェクト ID の複製が 3 回

## 変えたこと

### 返事の後も読みを持ち続ける（クライアント）

同期の呼び出しで、ただ一つ待たれていた返事を自分で読んだスレッドは（[read-ownership.md](read-ownership.md) の「クライアント（#67）」）、読み込みをタスクに返さず、サーバーの follow と同じ `Busy { watched: false }` にして持ち続ける（`Connection::keep_reading`）。次の呼び出しの `claim` は `Busy` から取るので、外すことも登録し直すこともない。

- **返す時**：ORB ごとに 1 本の見張り（`wire::Lag`、#206 と同じもの）が、`-ORBfollowLinger`（既定 1 ms）より長く次の呼び出しのない接続の読み込みをタスクに返す。サーバーからの `CloseConnection` などは、その後でタスクが読む（それより前に次の呼び出しがあれば、その呼び出しが読んで、今までどおり新しい接続で送り直す）
- **ほかの呼び出し元**：自分で読まずにタスクを待つ呼び出し元（ほかの返事も待たれている、async の呼び出し、タイムアウトの後など）は、待つ前に `Connection::resume` で読み込みをタスクに返す。持ち続けると決めたスレッドも、決めた後で待っている呼び出し元がいればすぐに返す（待つ側は登録してから `resume`、持つ側は `Busy` にしてから待つ側を見るので、どちらかが必ず気づく）
- 双方向 GIOP を申し出た接続（サーバーからの要求がタスク経由で届く）と `-ORBfollowLinger 0` では持ち続けない。Windows はスレッドが読まないので変わらない

`-ORBstatistics 1` の `reply_keeps` が持ち続けた回数、`keep_resumes` がほかの呼び出し元のために返した回数。見張りが返した回数は `follow_overdue` に入る。

### 待ってから読む

`Inbound::read_here` に最初の読み方（`FirstRead`）を渡す。クライアントは要求を送った直後なので、何も先読みしていなければ `poll` してから読む（`Wait`）。サーバーの follow は、前のメッセージを待ったかどうかで決める（`AsBefore`）：ping のように 1 つずつ届くなら次もまだ来ていないので待ってから読み、oneway のように続けて届くなら先に読む。

### 確保を減らす

- **IOR の解析は参照ごとに 1 回**：`ObjectRef` が、最後に呼んだ IOR（自分のものか、転送先）のアドレスの一覧（`Endpoint`）を持つ（クローンと共有）。IOR が変わったとき（転送）と TLS の設定が変わったときだけ作り直す。`Walk` は一覧を `Arc` で受け取り、添字で進む
- **コードセットの文脈は接続ごとに 1 回**：接続のコードセットは最初の要求で決まるので、その `ServiceContext` を接続が持つ
- **要求ヘッダは借りて書く**：`rustorb-giop` に `RequestParts`（操作名、`TargetRef`、サービスコンテキストの組、principal をすべて借りる）と `MessageEncoder::request_parts` を足した。サービスコンテキストは、コードセット、インターセプター、双方向 GIOP の 3 つの組をそのまま一つの列として書く。`MessageEncoder::request` は `RequestHeader` からこれを呼ぶので、書くバイト列は同じ（`tests/giop.rs` の `request_parts_match_request`）
- **接続の検索のキー**：`Endpoint` が `(host, port, transport)` のキーを持ち、`Orb::connection` はそれを借りて引く
- **使わない例外を作らない**：`Walk` の「使えるアドレスがない」と `attempt` の `TRANSIENT` は、要るときにだけ作る
- **サーバーのオブジェクト ID**：POA の実行中の数え（`running`）、`ObjectGuard`、`PortableServer::Current` の項目が一つの `Arc<[u8]>` を共有する

ping 1 回の `malloc` は、クライアントが 24 → 5 回（要求のバッファ、返事の読み込みと解読、待ち合わせの oneshot、操作名）、サーバーが 13 → 11 回。

### 時刻

接続の最後の利用時刻（アイドルの接続を閉じるため、呼び出しごとに 3〜4 回つける）は、Linux では `CLOCK_MONOTONIC_COARSE` で取る。アイドルの判定は 10 ms 以上の単位なので、数 ms の粗さは問題にならない。タイムアウトのない呼び出しは、今までどおり期限の時刻を取らない。

## 結果

クラウドの 4 コアの仮想マシン。`run-bench.py --quick --stats --impls rustorb` を main とこの変更で続けて回し、`compare-bench.py` で比べた（各 2 秒、3 回の中央値）。

| ケース | 値 | 前 | 後 |
| --- | --- | ---: | ---: |
| ping | p50 | 44.9 µs | 41.0 µs |
| ping | CPU / 呼び出し（クライアント・サーバー） | 25.7・30.8 µs | 19.5・30.0 µs |
| any | p50 | 64.7 µs | 55.8 µs |
| any | CPU / 呼び出し（クライアント・サーバー） | 35.3・39.7 µs | 28.9・37.4 µs |
| oneway | 毎秒の呼び出し | 27.3 万 | 29.2 万 |
| oneway | クライアントの CPU / 呼び出し | 2.52 µs | 1.54 µs |
| threads:4 | 毎秒の呼び出し | 3.64 万 | 3.89 万 |
| 同一プロセスの ping | p50 | 3.26 µs | 2.54 µs |
| get:1048576 | MB/s | 1,746 | 1,825 |

ping 1 回のシステムコール（`-ORBstatistics 1` の数）：クライアントは `writev` 1・`recv` 3（うち `EAGAIN` 2）・`poll` 1・`epoll_ctl` 2 の 7 回から、`writev` 1・`recv` 1・`poll` 1 の 3 回に。サーバーは `recv` 2（うち `EAGAIN` 1）・`poll` 1・`send` 1 の 4 回から 3 回に。

main とこの変更を交互に 4 回ずつ回した比較（別のスクリプト、各 2 秒）でも、ping のクライアントの CPU は 26.0 → 19.0 µs（−27%）、サーバーは 32.3 → 31.4 µs だった。

`cargo bench -p rustorb-core`（同じマシンで続けて 3 回）：`orb/echo_long_in_process` −6〜−7%、`orb/echo_long` −3%（ぶれの範囲）、`orb/oneway` は +9%・0%・−8% と回ごとにばらつき、ぶれより大きな差は見えない。`orb/echo_long` はクライアントとサーバーが同じプロセスで、往復の時間がほとんどカーネルの中なので、CPU の差が時間に出にくい。

### 届かなかったところ

#207 の終わりの条件は「CPU / ping を各側さらに 2 割以上減らす」。クライアントは届いたが、サーバーは 3% ほどにとどまる。サーバーの ping の CPU は、プロファイルで約 75% がカーネル（`sendto` が約 37%、そのうちループバックの受信処理とクライアントを起こす分が大半、`poll` で眠る分が約 29%）、ORB のユーザー空間は約 23% で、上位も 1% 未満の項目が並ぶ（`malloc`／`free`、`memmove`、ディスパッチ、POA の活動の数え）。システムコールは 1 回の要求で `poll`・`recv`・`send` の 3 回まで減っていて、これ以上はユーザー空間を半分にしても 1 割ほど。残りの候補：

- 要求の解読で、オブジェクトキー・操作名・サービスコンテキストを複製しない（`rustorb-giop` の `Message::Request` を借りる形にする。API の変更になる）
- POA の検索（`HashMap<Vec<u8>, _>` の SipHash、`Activity` の数え）を軽くする
- 実機（#213）ではカーネルの割合が小さいので、ユーザー空間の差がもっと大きく出る見込み。実機で測り直してから決める
