# 接続の読み込みの持ち主（leader/follower と、呼び出し元による返事の読み込み）

issue #66（サーバー）と #67（クライアント）。どちらも、接続の読み込みを I/O タスク（tokio）から一時的にスレッドへ渡し、要求 1 回あたりのスレッドの受け渡しを 1 回減らす。読み込みの持ち主をやり取りする仕組みは共通で、`crates/rustorb-core/src/wire.rs` の `Inbound` にある。

## なぜ

#64 の後のプロファイルでは、次の受け渡しが目立っていた（[load-testing.md](load-testing.md) の「まだ残っている差」）。

- サーバー：I/O タスクが要求を読み、アップコール用プールのスレッドを起こして渡す。プールのスレッドを起こす futex と切り替えが、多接続でサーバーの CPU の 3 割ほど
- クライアント：接続ごとの読み込みタスクが返事を読み、oneshot で呼び出し元のスレッドを起こす

サーバントを tokio のスレッドで動かさない設計（[poa-design.md](poa-design.md)）と、同期 API の呼び出し元が tokio の外のスレッドであることはそのまま守る。変えるのは「誰が読むか」だけである。

## 持ち主

接続ごとに、読み込みの持ち主は次のどれかである（`wire::Holder`）。

| 状態 | 意味 |
| --- | --- |
| `Task { active }` | I/O タスクが持つ。`active` はタスクが読んでいるか、読んだものを処理している間 |
| `Thread` | スレッドが一つだけ読んでいる（または `poll(2)` で読めるのを待っている） |
| `Busy` | 直前に読んだスレッドが、読んだ要求を処理している。処理が終われば読みに戻るつもりでいる |

守ること：

1. 同時に読むのは一つだけ。スレッドが持ち主になれるのは、タスクが待っているとき（`Task { active: false }`）か `Busy` のときだけ（`Inbound::claim`）。タスクは `Thread` の間は読まない
2. 読みかけのデータ（先読みバッファ、大きなメッセージの途中、フラグメントの組み立て）は持ち主と一緒に移る。`Inbound` の `ReadSide` に置き、読む側が錠を取って使う
3. 届いたデータが誰にも読まれずに残ることはない（次の節）

錠の順は `holder` → `side`。

## 届いたデータを取りこぼさないために

タスクはランタイムのレディネス（epoll、エッジトリガー）で起こされ、`try_io` で読む（`WouldBlock` でレディネスが消える）。スレッドはランタイムを通さず、ソケットを直接 `recv` し、`poll(2)` で待つ。スレッドが読んでいる間にデータが届くと、タスクも起こされる。

- タスクが起きて持ち主が `Thread` なら、そのデータはスレッドが読むので、タスクはレディネスを消して待ちに戻る
- 持ち主が `Busy` なら、タスクは届いた分を読み、何かあれば持ち主になる（`Task { active: true }`）。同じ接続に多重化された次の要求を、スレッドの処理が終わるのを待たずに読むため。スレッドは処理の後で持ち主に戻れず、プールに戻る
- スレッドが持ち主を返すとき（`release`、`busy`）は、`holder` の錠の中でソケットに届いている分を先読みバッファに読み込んでから返す。何か残っていればタスクを起こし（`Notify`）、タスクの次の読み込みはレディネスがなくてもソケットを読む（`handed_back`）。錠の中で読むので、「タスクがレディネスを消した後に届いたのに、スレッドは読まずに返した」ということが起きない。返した後に届いたデータは、新しいエッジでタスクを起こす

大きなメッセージ（先読みの 16 KiB を超えるもの）は、ヘッダが見えた時点でスレッドが読むのをやめ、タスクに返す。細切れに届く本体を `poll` で一つずつ待つより、タスクがまとめて読むほうが起床が少ない。また、本体のバッファをどのスレッドで確保するかで glibc の malloc の振る舞い（mmap の閾値とトリム）が変わり、呼び出し元のスレッドで確保するとページフォールトが毎回出て 1 MiB の往復が 2 倍遅くなった。大きなメッセージの改善は #68 で扱う。

スレッドがソケットを待てるのは `poll(2)` がある Unix だけで、それ以外（Windows）では `claim` が常に失敗し、今までどおりタスクが読む。

## サーバー（#66）

ORB_CTRL_MODEL の POA の要求をプールのスレッドで処理し終えたら、そのスレッドは同じ接続の次の要求を自分で読む（`Server::follow`）。

1. サーバーが止まりかけていない、プールに待っている仕事がない、の両方を確かめる。待っている仕事があれば、それはほかの接続の要求なので、プールに戻ってそれを取る（一つの接続がスレッドを占有してほかを飢えさせない）
2. 接続ごとの要求数の上限（`max_requests_per_connection`）の枠を `try_acquire` で先に取る。取れなければ読まない（読んだのに処理できない要求を抱えないため）
3. `claim` で持ち主になり、`FOLLOW_LINGER`（1 ms）まで次のメッセージを待つ。順に呼ぶクライアントは、返事を受け取ってから次の要求を送るので、ループバックや LAN では往復時間のうちに届く。届かなければ持ち主をタスクに返してプールに戻る
4. 読んだのが Request なら `busy` にしてから処理する。POA を探し（アダプターアクティベーターもこのスレッドで呼んでよい）、POA マネージャーがすぐに通す（active）なら、このスレッドでそのままアップコールする。holding で後回しになった要求は、マネージャーが通したときに今までどおりプールに積む。ORB_CTRL_MODEL 以外の POA の要求は、今までどおりその方針のスレッドに渡す
5. LocateRequest と CancelRequest もこのスレッドで処理する。CancelRequest はフラグメントの組み立てと返事の取り消しの両方に効く（`ServerConn::cancel_request`）
6. CloseConnection、MessageError、読み込みの失敗や接続断は、スレッドでは処理せず `ReadSide` に置いてタスクに返す。接続を閉じる手順（`serve` の後始末、`MessageError` の送信）はタスクの側にしかない
7. 1〜6 を `FOLLOW_LIMIT`（64）回まで繰り返す。上限に来たら持ち主を返し、次の要求はタスク経由でプールに入る

スレッドが follow している間も、ほかのスレッドは同じ接続の要求を処理できる。`Busy` の間に届いた要求はタスクが読んでプールに積むので、多重化された接続でも要求は並行に処理される。

返事の書き込みは #64 のまま（作ったスレッドが `try_write`、残りは書き込みタスク）。

follow の待ちの間、そのスレッドはプールのほかの仕事をしない。プールは空いたスレッドがなければ新しいスレッドを起こす（上限 `max_server_threads`）ので、接続が多いとスレッド数は接続数に近づく。プールが上限に達していれば、新しい仕事はキューに入り、待っているスレッドは 1 ms 以内に戻る。

## クライアント（#67）

呼び出し元は要求を送った後、その接続で返事を待っているのが自分だけで、読み込みタスクが待っているなら、自分のスレッドで返事を読む（`Connection::read_reply_here`）。

1. 待っている呼び出しが自分だけか確かめ、`claim` で持ち主になる
2. 持ち主になった後で、自分の返事がまだ届いていないこと（待ち一覧に自分が残っていること）を確かめ直す。確かめてから持ち主になるまでの間に、タスクが返事を読んで渡していることがある。これを見落とすと、もう来ない返事を待ち続ける（16 接続のベンチマークで見つかった不具合。`tests/stress.rs` の `back_to_back_calls_hand_the_reading_over` で確かめる）
3. 呼び出しのタイムアウト（[timeouts.md](timeouts.md)）までソケットを待って読む。読んだのがほかの呼び出しへの返事なら、その呼び出しの oneshot に渡して読み続ける。自分の返事なら持ち主を返して終わる
4. タイムアウトになれば持ち主を返し、今までどおり `CancelRequest` を送って `TIMEOUT` で戻る
5. CloseConnection や接続断、要求（双方向でないので来ないはず）を読んだら、`ReadSide` に置いてタスクに返し、自分は oneshot で待つ。タスクが接続を閉じ、待っている呼び出しに `Closed` を渡す
6. 接続が失敗扱いになったとき（書き込みの失敗など）は、読み込みの向きを `shutdown` して、読んでいる呼び出し元の `poll` を終わらせる

同期 API の呼び出しは `Orb::block_on` で呼び出し元のスレッドの上で動き、`block_on` はランタイムのスレッドからは呼べない。だから `attempt` の中で `poll(2)` で止まっても、止まるのは呼び出し元自身のスレッドだけで、ランタイムのスレッドは止まらない。

ほかの呼び出しも同じ接続で返事を待っているときは、今までどおりタスクが読む。持ち主になった呼び出し元が、後から来た呼び出しの返事も読んで渡すことはあるが、自分の返事を受け取ったら持ち主を返し、残りはタスクが読む。

## 結果

`cargo bench -p rustorb-core`（4 コアのサンドボックス、変更前を `--save-baseline before` で保存して比べた）。

| ベンチマーク | 変更前 | 変更後 |
| --- | ---: | ---: |
| `orb/echo_long`（1 回ずつ） | 71 µs | 46 µs |
| `orb/echo_long_connections/16` | 毎秒 7.7 万回 | 毎秒 9.4 万回 |
| `orb/echo_octets_1MiB` | 0.79 ms | 0.86 ms |

1 MiB は大きなメッセージをタスクに返すようにした後の値で、ほぼ変わらない（ぶれの範囲を少し超える程度）。`interop/run-load.sh` 相当の測り方での前後は [load-testing.md](load-testing.md) に記録する。

## 設定

follow の待ち時間と連続の上限は `OrbOptions` で変えられる（#86）。既定は 1 ms と 64 回で、#66 のときの定数と同じ。

| `OrbOptions` | 引数 | 既定 | 意味 |
| --- | --- | --- | --- |
| `follow_linger` | `-ORBfollowLinger US`（マイクロ秒） | 1 ms | 処理を終えたスレッドが次の要求を待つ時間。0 で follow しない |
| `follow_limit` | `-ORBfollowLimit N` | 64 | 1 本のスレッドが続けて読む要求の数。0 で follow しない |

待ち時間を長くすると、間隔の空いた呼び出しでもスレッドの上で読めるが、そのスレッドはその間ほかの仕事をしない。接続が多くプールの上限が小さいときは、短くするか 0 にする。`tests/stress.rs` の `back_to_back_calls_hand_the_reading_over` と `back_to_back_calls_without_follow` は、follow のあり・なしで同じ呼び出しを繰り返す（サンドボックスのデバッグビルドで毎秒約 1.0 万回と 0.8 万回）。

## しないこと（#86 で決めた）

- **Windows**：スレッドがソケットを待つのに `WSAPoll` を使う形にはしない。Windows の tokio（mio）は AFD でソケットの準備を受け取り、mio 自身の読み書きが `WouldBlock` を返したときにだけ次の通知を頼み直す。スレッドが mio を通さずにソケットを読むと、タスクに戻したときに通知が来ないまま止まるおそれがあり、手元で試すことも測ることもできない。Windows では今までどおりタスクが読み、プールに渡す
- **スレッドが読んでいる間のタスクの起床**：スレッドが読んでいる間も、届いたデータでタスクが起こされる。タスクは持ち主を見て何も読まずに戻るので読み込みには影響しない。起こさないようにするには、ソケットを epoll から外すか（tokio にその API はない）、タスクが読み込みの返却だけを待つようにする必要がある。後者は要求ごとに `busy` でタスクへの通知が要り、今の空振りの起床と手間が変わらないので、このままにする
