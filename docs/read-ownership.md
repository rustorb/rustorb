# 接続の読み込みの持ち主（leader/follower と、呼び出し元による返事の読み込み）

issue #66（サーバー）と #67（クライアント）。どちらも、接続の読み込みを I/O タスク（tokio）から一時的にスレッドへ渡し、要求 1 回あたりのスレッドの受け渡しを 1 回減らす。読み込みの持ち主をやり取りする仕組みは共通で、`crates/rustorb-core/src/wire.rs` の `Inbound` にある。

## なぜ

#64 の後のプロファイルでは、次の受け渡しが目立っていた（[load-testing.md](load-testing.md) の「まだ残っている差」）。

- サーバー：I/O タスクが要求を読み、アップコール用プールのスレッドを起こして渡す。プールのスレッドを起こす futex と切り替えが、多接続でサーバーの CPU の 3 割ほど
- クライアント：接続ごとの読み込みタスクが返事を読み、oneshot で呼び出し元のスレッドを起こす

サーバントを tokio のスレッドで動かさない設計（[poa-design.md](poa-design.md)）と、同期 API の呼び出し元が tokio の外のスレッドであることはそのまま守る。変えるのは「誰が読むか」だけである。

## 持ち主

接続ごとに、読み込みの持ち主は次のどれかである（`wire::Holder`）。

| 状態 | 意味 |
| --- | --- |
| `Task { active }` | I/O タスクが持つ。`active` はタスクが読んでいるか、読んだものを処理している間 |
| `Thread` | スレッドが一つだけ読んでいる（または `poll(2)` で読めるのを待っている） |
| `Busy { watched }` | 直前に読んだスレッド（または I/O タスクが要求を渡したスレッド、#206）が、その要求を処理している。処理が終われば読みに戻るつもりでいる。`watched` でなければ読み込みはポーラーから外れたままで、その間は誰も読まない（[処理の間も読みを持ち続ける](#処理の間も読みを持ち続ける206)） |

守ること：

1. 同時に読むのは一つだけ。スレッドが持ち主になれるのは、タスクが待っているとき（`Task { active: false }`）か `Busy` のときだけ（`Inbound::claim`）。タスクは `Thread` の間は読まない
2. 読みかけのデータ（先読みバッファ、大きなメッセージの途中、フラグメントの組み立て）は持ち主と一緒に移る。`Inbound` の `ReadSide` に置き、読む側が錠を取って使う
3. 届いたデータが誰にも読まれずに残ることはない（次の節）

錠の順は `holder` → `side`。

## 届いたデータを取りこぼさないために

タスクはランタイムのレディネス（epoll、エッジトリガー）で起こされ、`try_io` で読む（`WouldBlock` でレディネスが消える）。スレッドはランタイムを通さず、ソケットを直接 `recv` し、`poll(2)` で待つ。Unix では、スレッドが持ち主の間は読み込みをポーラーから外すので、届いたデータでタスクは起こされない（[epoll から外す](#epoll-から外す205)）。

- それでもタスクが起きて（外す前にポーラーが受け取っていた分）持ち主が `Thread` なら、そのデータはスレッドが読むので、タスクはレディネスを消して待ちに戻る
- 持ち主が `Busy { watched: true }` なら、タスクは届いた分を読み、何かあれば持ち主になる（`Task { active: true }`）。同じ接続に多重化された次の要求を、スレッドの処理が終わるのを待たずに読むため。スレッドは処理の後で持ち主に戻れず、プールに戻る
- スレッドが持ち主を返すとき（`release`、`busy`）は、`holder` の錠の中でソケットに届いている分を先読みバッファに読み込んでから返す。何か残っていればタスクを起こし（`Notify`）、タスクの次の読み込みはレディネスがなくてもソケットを読む（`handed_back`）。錠の中で読むので、「タスクがレディネスを消した後に届いたのに、スレッドは読まずに返した」ということが起きない。返した後に届いたデータは、新しいエッジでタスクを起こす

大きなメッセージ（先読みの 16 KiB を超えるもの）は、ヘッダが見えた時点でスレッドが読むのをやめ、タスクに返す。細切れに届く本体を `poll` で一つずつ待つより、タスクがまとめて読むほうが起床が少ない。また、本体のバッファをどのスレッドで確保するかで glibc の malloc の振る舞い（mmap の閾値とトリム）が変わり、呼び出し元のスレッドで確保するとページフォールトが毎回出て 1 MiB の往復が 2 倍遅くなった。大きなメッセージの改善は #68 で扱う。

スレッドがソケットを待てるのは `poll(2)` がある Unix だけで、それ以外（Windows）では `claim` が常に失敗し、今までどおりタスクが読む。

## サーバー（#66）

ORB_CTRL_MODEL の POA の要求をプールのスレッドで処理し終えたら、そのスレッドは同じ接続の次の要求を自分で読む（`Server::follow`）。

1. サーバーが止まりかけていない、プールに待っている仕事がない、の両方を確かめる。待っている仕事があれば、それはほかの接続の要求なので、プールに戻ってそれを取る（一つの接続がスレッドを占有してほかを飢えさせない）
2. 接続ごとの要求数の上限（`max_requests_per_connection`）の枠を `try_acquire` で先に取る。取れなければ読まない（読んだのに処理できない要求を抱えないため）
3. `claim` で持ち主になり、`FOLLOW_LINGER`（1 ms）まで次のメッセージを待つ。順に呼ぶクライアントは、返事を受け取ってから次の要求を送るので、ループバックや LAN では往復時間のうちに届く。届かなければ持ち主をタスクに返してプールに戻る
4. 読んだのが Request なら `busy` にしてから処理する。POA を探し（アダプターアクティベーターもこのスレッドで呼んでよい）、POA マネージャーがすぐに通す（active）なら、このスレッドでそのままアップコールする。holding で後回しになった要求は、マネージャーが通したときに今までどおりプールに積む。ORB_CTRL_MODEL 以外の POA の要求は、今までどおりその方針のスレッドに渡す
5. LocateRequest と CancelRequest もこのスレッドで処理する。CancelRequest はフラグメントの組み立てと返事の取り消しの両方に効く（`ServerConn::cancel_request`）
6. CloseConnection、MessageError、読み込みの失敗や接続断は、スレッドでは処理せず `ReadSide` に置いてタスクに返す。接続を閉じる手順（`serve` の後始末、`MessageError` の送信）はタスクの側にしかない
7. 1〜6 を `FOLLOW_LIMIT`（64）回まで繰り返す。上限に来たら持ち主を返し、次の要求はタスク経由でプールに入る

スレッドが follow している間も、ほかのスレッドは同じ接続の要求を処理できる。#206 からは、スレッドが要求を処理している間に届いた要求は、そのスレッドが戻って読むか、処理が長引けば（follow の待ち時間を過ぎれば）タスクが読んでプールに積む（[処理の間も読みを持ち続ける](#処理の間も読みを持ち続ける206)）。

返事の書き込みは #64 のまま（作ったスレッドが `try_write`、残りは書き込みタスク）。

follow の待ちの間、そのスレッドはプールのほかの仕事をしない。プールは空いたスレッドがなければ新しいスレッドを起こす（上限 `max_server_threads`）ので、接続が多いとスレッド数は接続数に近づく。プールが上限に達していれば、新しい仕事はキューに入り、待っているスレッドは 1 ms 以内に戻る。

## クライアント（#67）

呼び出し元は要求を送った後、その接続で返事を待っているのが自分だけで、読み込みタスクが待っているなら、自分のスレッドで返事を読む（`Connection::read_reply_here`）。

1. 待っている呼び出しが自分だけか確かめ、`claim` で持ち主になる
2. 持ち主になった後で、自分の返事がまだ届いていないこと（待ち一覧に自分が残っていること）を確かめ直す。確かめてから持ち主になるまでの間に、タスクが返事を読んで渡していることがある。これを見落とすと、もう来ない返事を待ち続ける（16 接続のベンチマークで見つかった不具合。`tests/stress.rs` の `back_to_back_calls_hand_the_reading_over` で確かめる）
3. 呼び出しのタイムアウト（[timeouts.md](timeouts.md)）までソケットを待って読む。読んだのがほかの呼び出しへの返事なら、その呼び出しの oneshot に渡して読み続ける。自分の返事なら持ち主を返して終わる
4. タイムアウトになれば持ち主を返し、今までどおり `CancelRequest` を送って `TIMEOUT` で戻る
5. CloseConnection や接続断、要求（双方向 GIOP の接続でなければ来ないはず、[bidir-giop.md](bidir-giop.md)）を読んだら、`ReadSide` に置いてタスクに返し、自分は oneshot で待つ。タスクが接続を閉じ、待っている呼び出しに `Closed` を渡す
6. 接続が失敗扱いになったとき（書き込みの失敗など）は、読み込みの向きを `shutdown` して、読んでいる呼び出し元の `poll` を終わらせる

同期 API の呼び出しは `Orb::block_on` で呼び出し元のスレッドの上で動き、`block_on` はランタイムのスレッドからは呼べない。だから `attempt` の中で `poll(2)` で止まっても、止まるのは呼び出し元自身のスレッドだけで、ランタイムのスレッドは止まらない。

ほかの呼び出しも同じ接続で返事を待っているときは、今までどおりタスクが読む。持ち主になった呼び出し元が、後から来た呼び出しの返事も読んで渡すことはあるが、自分の返事を受け取ったら持ち主を返し、残りはタスクが読む。

## epoll から外す（#205）

#66・#67 の形では、スレッドが読んでいる間もソケットはランタイムのポーラー（Linux の epoll、macOS の kqueue）に登録されたままで、データが届くたびに I/O スレッド（`rustorb-io`）が起こされていた。タスクは持ち主を見て何も読まずに戻るが、起床そのものが両側で CPU の約 2 割を使い、カーネルの `sock_def_readable` も起こす相手が 2 つ（スレッドの `poll` とポーラー）になっていた（[perf-plan.md](perf-plan.md) の「分かったこと」2）。

Unix では、スレッドが持ち主の間（`Thread`）は読み込みをポーラーから外す。

- 分割した接続の読み書きは、tokio の `TcpStream` のままだと一つの登録（読み・書きの両方）を共有するので、`into_std` で外すと書き込みの待ちまで外れてしまう。そこで `sock::Stream::into_split` で tokio の登録を外し（`into_std`）、読み書きを別々に登録し直す。書き込み側はソケットそのものを書き込みだけ（`Interest::WRITABLE`）で、読み込み側はソケットを `dup` した別の記述子を読み込みだけ（`Interest::READABLE`）で登録する（ポーラーは記述子ごとに登録を持つので、読み込みの登録だけを外せる）。届いたデータで書き込み側の登録が起こされることはない
- `Inbound::claim` で持ち主になったスレッドが読み込みの登録を外す（`ReadHalf::unwatch`、`epoll_ctl` の削除）。`release` と `busy` で持ち主をタスクに戻すとき、または `Busy` にするとき（多重化された次の要求をタスクが読めるように）に登録し直す（`ReadHalf::watch`）。登録し直した時点でソケットに届いている分は、ポーラーがすぐに読めると知らせる（epoll の追加は今の状態を調べる）ので、`release` の先読みと登録の間に届いたデータも取りこぼさない
- 登録を外している間、タスクは `back`（持ち主を返したときの通知）と、登録がないので止まったままの読み込みの待ちで待っている。登録し直すスレッドは、タスクが最後に待ったときの waker を新しい登録に渡す（`poll_read_ready` をその waker で呼ぶ）。タスクを起こすのは、そのときもう読めるときだけ
- 登録し直しに失敗したら、タスクの待ちがそのエラーで終わり、接続を閉じる

`epoll_ctl` は呼び出しごとではなく持ち主の受け渡しごとに 1 回ずつ。クライアントは 1 回の呼び出しで外す・戻すの 2 回。サーバーの follow は #205 の時点では要求ごとに `Busy` で戻し、次の `claim` で外すので 2 回だったが、#206 で要求を処理する間も外したままにしたので、follow が続く間は 0 回。tokio は外した登録を 16 個ごとにまとめて片づけるので、そのときだけ I/O スレッドが起きる（呼び出し 8 回に 1 回ほど）。`-ORBstatistics 1` の `watches` と `unwatches` がこの回数、`task_wakeups_thread_reads` が残った空振りの起床（外す前にポーラーが受け取っていた分）を数える。

Windows はスレッドが読まないので、今までどおり tokio の `TcpStream` を分割して使う。

結果（クラウドの 4 コアの仮想マシン、`run-bench.py --quick --stats` を main とこの変更で続けて回し、`compare-bench.py --counters` で比べた。3 回の中央値）：

## 設定

follow の待ち時間と連続の上限は `OrbOptions` で変えられる（#86）。既定は 1 ms と 64 回で、#66 のときの定数と同じ。

| `OrbOptions` | 引数 | 既定 | 意味 |
| --- | --- | --- | --- |
| `follow_linger` | `-ORBfollowLinger US`（マイクロ秒） | 1 ms | 処理を終えたスレッドが次の要求を待つ時間。0 で follow しない。#206 からは、スレッドが要求を処理している間、同じ接続の後ろの要求をタスクに読ませずに待たせる長さでもある（長引けば待ち時間の 2 倍までにタスクが読む） |
| `follow_limit` | `-ORBfollowLimit N` | 64 | 1 本のスレッドが続けて読む要求の数。0 で follow しない |

待ち時間を長くすると、間隔の空いた呼び出しでもスレッドの上で読めるが、そのスレッドはその間ほかの仕事をしない。接続が多くプールの上限が小さいときは、短くするか 0 にする。`tests/stress.rs` の `back_to_back_calls_hand_the_reading_over` と `back_to_back_calls_without_follow` は、follow のあり・なしで同じ呼び出しを繰り返す（サンドボックスのデバッグビルドで毎秒約 1.0 万回と 0.8 万回）。

## しないこと（#86 で決めた）

- **Windows**：スレッドがソケットを待つのに `WSAPoll` を使う形にはしない。Windows の tokio（mio）は AFD でソケットの準備を受け取り、mio 自身の読み書きが `WouldBlock` を返したときにだけ次の通知を頼み直す。スレッドが mio を通さずにソケットを読むと、タスクに戻したときに通知が来ないまま止まるおそれがあり、手元で試すことも測ることもできない。Windows では今までどおりタスクが読み、プールに渡す

## 処理の間も読みを持ち続ける（#206）

#205 の後も、サーバーの oneway（返事のない要求が続けて届く）では follow がまったく効いていなかった（[perf-plan.md](perf-plan.md) の基準の値）。I/O タスクが要求を読んでプールに渡すと、タスクはそのまま次の要求を読み続ける。渡されたスレッドが要求を処理し終えて `claim` するころには、タスクが次の要求を読んでいて（`Task { active: true }`）`claim` が失敗し、要求ごとにプールへの受け渡しとスレッドの起床が 1 回ずつ起きていた。follow で読めた場合も、要求を処理する間は `Busy` で読み込みをポーラーに戻していたので、その間に届いた次の要求はタスクが読んでプールに渡していた。

そこで、要求を処理する間も、読み込みはそのスレッドが持ち続ける。

- **タスクが読みを譲る**（`Inbound::pause`）：I/O タスクが読んだ要求を、follow するプールのスレッドに渡すとき（ORB_CTRL_MODEL の POA で、POA マネージャーがすぐに通したとき、`schedule_upcall`）、渡す前に持ち主を `Busy { watched: false }` にして読み込みをポーラーから外す。スレッドが読んで処理しているのと同じ形になり、タスクは次の要求を読まない。スレッドは処理の後で `claim` し（`Busy` からなので必ず取れる）、次の要求を先読みバッファかソケットから読む。タスクが読んでいるときだけ譲る（`on_request` から `route` している間だけ立つスレッドローカルで見分ける）ので、ほかのスレッドが後から（holding の POA マネージャーが通したときなど）渡した要求では譲らない
- **処理の間も外したまま**（`Inbound::busy` の `off`）：follow で読んだ要求を処理する間も `Busy { watched: false }` にし、ソケットの読み込みも登録し直しもしない。続けて届いた要求は、スレッドが戻ってから読む。受け渡しも起床も `epoll_ctl` もない
- **長い処理の見張り**（`wire::Lag`）：スレッドがアップコールで長く止まると、その後ろの要求を誰も読まない。サーバーごとに 1 本の見張りのスレッド（`rustorb-lag`）が、`Busy { watched: false }` の接続を follow の待ち時間（`-ORBfollowLinger`、既定 1 ms）ごとに見て、それより長く `Busy` のままの接続の読み込みをタスクに戻す（`Inbound::overdue`）。ソケットに届いている分を先読みに読み込み、ポーラーに登録し直し、何か読めていればタスクを起こす（`release` と同じ手順）。読めていなければ `Busy { watched: true }` にして、届けばタスクが読む。スレッドは処理の後、タスクが待っていれば今までどおり持ち主に戻れる。後ろの要求が待たされるのは待ち時間の 2 倍（既定 2 ms）まで。見張りは、`Busy` の始まり（`turns`）が 64 回見る間に一度もなかった接続を一覧から外し、一覧が空なら眠る。接続を一覧に入れるのは、一覧にないときだけ（`listed`）なので、要求ごとに錠は取らない
- **双方向 GIOP の接続**では今までどおり（`busy` の `off` なし、譲らない）。アップコールがその接続でクライアントを呼び出すと、その返事も同じ接続で届くので、処理の間もタスクが読んでいなければならない
- 接続の読み込みを止める（`Inbound::shutdown`）ときは、`Busy { watched: false }` ならすぐにタスクに戻す。サーバーが止まるときにプールが捨てた仕事のスレッドは戻ってこないため

一つの接続に多重化された要求は、短いものなら 1 本のスレッドが順に処理する（今までは、届くたびにタスクが読んで別のスレッドに渡していた）。長いものがあれば、見張りが待ち時間の後でタスクに戻すので、後ろの要求はほかのスレッドで並行に動く（`tests/stress.rs` の `a_long_call_does_not_hold_up_the_calls_behind_it`、見張りがなければ 0.9 秒待たされる）。

oneway の要求では、サーバントが返った後に返事のメッセージを組み立てない（`ServerReply::finish` を飛ばす）。

`-ORBstatistics 1` の `follow_pauses` がタスクが読みを譲った回数、`follow_overdue` が見張り（または `shutdown`）がタスクに戻した回数。follow をしない（`-ORBfollowLinger 0` か `-ORBfollowLimit 0`）なら、譲ることも見張りもなく、今までどおりタスクがすべて読む。Windows ではスレッドが読まないので譲らない。

結果（クラウドの 4 コアの仮想マシン、`run-bench.py --quick --stats --impls rustorb` を main とこの変更で続けて回し、`compare-bench.py --counters` で比べた。各 2 秒、3 回の中央値）：

| ケース | 値 | 前 | 後 |
| --- | --- | ---: | ---: |
| oneway | 毎秒の呼び出し | 5.54 万 | 27.95 万 |
| oneway | サーバーの CPU / 呼び出し | 29.5 µs | 3.58 µs |
| oneway | サーバーのコンテキストスイッチ / 呼び出し | 2.02 | 0.06 |
| threads:4 | 毎秒の呼び出し | 2.88 万 | 3.59 万 |
| threads:4 | サーバーの CPU / 呼び出し | 38.0 µs | 17.1 µs |
| threads:4 | サーバーのコンテキストスイッチ / 呼び出し | 2.00 | 0.49 |
| ping | p50 | 51.2 µs | 45.8 µs |
| ping | サーバーの CPU / 呼び出し | 36.4 µs | 31.9 µs |
| ping | サーバーの `epoll_ctl`（`watches`+`unwatches`）/ 呼び出し | 1.97 | 0.03 |
| get:1048576 | MB/s | 1,605 | 1,760・1,628（2 回） |

oneway では、要求ごとのプールへの受け渡し（`pool_jobs`）と起床（`pool_wakes`）が 1.0 から 0.015（follow の上限の 64 回に 1 回）に、`claim` の失敗が 0.90 から 0 になった。見張りのスレッドは、接続が動いている間 1 ms ごとに起きる（ping で 1 回あたり 0.05 回、1 MiB の get で 0.6 回のコンテキストスイッチ）。

follow をしないサーバー（`-ORBfollowLinger 0`）の oneway は、前 8.8 万回/s、後 8.6 万回/s（3 回の中央値、ぶれの範囲）で変わらない。
