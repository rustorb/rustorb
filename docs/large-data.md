# 大きなデータの受信（#211）

Nov 27, 2026 · @ysuga · [速度の改善の計画](perf-plan.md)の段 8（issue [#211](https://github.com/rustorb/rustorb/issues/211)）

クライアントが大きな `sequence<octet>` を受け取るときのコピーと起床を減らした。core に共有で受け取る記述子と、大きなメッセージの途中で起きる回数を減らす仕組みを足した。生成コードの側は [rustorb-idl](https://github.com/rustorb/rustorb-idl) の `-Wbshared_octets`（次の版から）。

## 見えていたこと

クラウドの 4 コアの仮想マシンで、rustorb どうしの `get:1048576`（1 MiB を受け取る）は 1.24 GB/s、p50 は 815 µs だった。クライアントの CPU は 1 回 490 µs。`perf record` では次のとおり。

| | クライアントの CPU |
| --- | ---: |
| カーネルの受信のコピー（`_copy_to_iter`） | 20% |
| 生成コードの `Vec<u8>` へのコピー（`Octet::read_items` の `to_vec`） | 19% |
| 起床とスケジューラー（`finish_task_switch`、`_raw_spin_unlock_irqrestore` など） | 約 30% |

- 受け取った本体は前から `Arc<Vec<u8>>` で共有していて（#64・#68）、`Decoder::read_octet_seq_shared` ならコピーせずに取り出せる。ただ生成コードは `Vec<u8>` を返すので、ここで必ず 1 MiB をコピーしていた
- 大きなメッセージ（16 KiB の先読みより大きいもの）は I/O タスクが読む（[read-ownership.md](read-ownership.md)）。データが届くたびにタスクが起き、1 回の受信で `recv` が約 9 回、そのうち 3 回は `EAGAIN` だった
- 受信のバッファの確保は重くなかった。TCP 越しの `get` でページフォールトは 1 回あたり 0.5 回ほどで、glibc が解放された 1 MiB をそのまま使い回している

## 変えたこと

### 共有で受け取る記述子（`idl::SharedOctets`）

`rustorb_core::idl::SharedOctets` は、`sequence<octet>` を [`Octets`](../crates/rustorb-cdr/src/octets.rs)（`rustorb_core::Octets`）で表す記述子。

- 受け取るとき：4 KiB（`SHARE_MIN`）以上なら、受け取ったメッセージのバッファを指すだけでコピーしない。`Octets` を持っている間はメッセージのバッファも残る
- 送るとき：4 KiB 以上なら、メッセージに写さず、そのままの所から書く（`write_octet_seq_shared`、ベクタの書き込み）
- ワイヤ上のバイトと TypeCode は `Sequence<Octet>` と同じ。呼び出しの片側だけが使ってもよい

rustorb-idl の `-brust -Wbshared_octets` は、上限のない `sequence<octet>`（typedef も、struct のメンバーも）をこれに対応させる。値の型は `rustorb_core::Octets`、`in` 引数は `&Octets`（スライスではない：送るときに共有するため）。`Vec<u8>` から作るのはコピーなし（`Octets::from(v)`）、`Vec<u8>` に戻すのは、ほかに共有していなければコピーなし（`into_vec`）。上限つきの `sequence<octet, N>` は今のまま `Vec<u8>`。既定は今のまま（`Vec<u8>`）で、[Rust のマッピング](rust-mapping.md)も変えない。DDS の出力（`-Wbdds`・`-Wbdds_only`）とは一緒に使えない。

### 大きなメッセージの途中で起きる回数（Linux）

大きなメッセージを読んでいる途中で読むものがなくなったら、ソケットの `SO_RCVLOWAT` を「残りの長さ（256 KiB まで）」にし、読み終えたら 1 に戻す。カーネルは、それだけのバイトが届くまで（またはストリームが終わるか失敗するまで）ソケットを読めるとしないので、I/O タスク（epoll）も、読んでいるスレッド（`poll`）も、細切れの到着のたびには起きない。

- 読むときは、届いている分がそれより少なくても返ってくる（ノンブロッキングの `recv`）。待つ所だけが変わる
- 残りの長さより大きくはしないので、メッセージの最後の部分を待ち続けることはない。Linux は受信バッファの半分より大きい値をそこまで下げる
- TLS の接続では使わない（読み手がまだ要るバイト数と、ソケットに要るバイト数が違う）。Linux の TCP だけで、macOS・Windows と giop:unix は今のまま
- 変えた回数は `stats` の `low_water_sets`（大きなメッセージ 1 つで 2 回）

試し（同じサーバーに、ありとなしを交互に、各 2 秒を 3 回）で、共有で受け取るクライアントの `get:1048576` の p50 は 520〜560 µs から 400〜420 µs になった。256 KiB と 1 MiB で差は見えなかった。`Vec<u8>` で受け取るクライアントでは、コピーの方が重く、速さはほぼ変わらない（CPU は少し減る）。

### しなかったこと

- **受信のバッファの再利用**：上のとおり、TCP 越しではページフォールトがほとんどなく、効く所がない。同一プロセスの `get:1048576` は 1 回あたり約 480 回のページフォールト（CPU の 4 割）があるが、これはサーバントが作る 1 MiB の `Vec`（アップコールのスレッドで確保し、呼び出し元のスレッドで解放する）の glibc の扱いで、受信のバッファではない
- **呼び出し元のスレッドが大きなメッセージを自分で読む**：試したが、差は 4% ほどでぶれの範囲だった。今のまま I/O タスクが読む

## 測った結果

クラウドの 4 コアの仮想マシン（Intel Xeon 2.1 GHz）、`run-bench.py --impls rustorb --stats`、各ケース 2 秒の 3 回の中央値。main と、この変更（生成コードは `Vec<u8>` のまま）と、この変更に `-Wbshared_octets` で生成し直したベンチ（クライアントもサーバーも `Octets`）を交互に 2 回ずつ回した。値は 2 回のうち 1 回目、括弧は 2 回目。

| ケース | main | この変更（`Vec<u8>`） | `-Wbshared_octets` |
| --- | ---: | ---: | ---: |
| `get:1048576` MB/s | 1,286（1,234） | 1,251（1,234） | 2,378（2,198） |
| `get:1048576` p50 µs | 786（817） | 812（813） | 414（454） |
| `get:1048576` クライアントの CPU µs | 483（492） | 484（495） | 289（299） |
| `put:1048576` MB/s | 1,352（1,275） | 1,393（1,400） | 2,376（2,352） |
| `octets:1048576` MB/s | 828（803） | 801（834） | 2,529（2,491） |
| `octets:8388608` MB/s | 726（738） | 731（748） | 2,724（2,670） |
| 同一プロセスの `octets:1048576` MB/s | 1,518（1,566） | 1,604（1,467） | 2,655（2,751） |
| ping p50 µs | 44.6（46.1） | 47.6（47.6） | 49.0（45.6） |
| oneway 回/s | 37.5 万（38.7 万） | 37.3 万（37.8 万） | 35.8 万（38.0 万） |
| threads:4 回/s | 11.8 万（11.9 万） | 12.0 万（11.5 万） | 12.1 万（11.6 万） |

- `-Wbshared_octets` で、`get:1048576` はクラウドで 1.25 GB/s から 2.2〜2.4 GB/s（+80% ほど）になった。クライアントの CPU は 4 割減。共有だけ（`SO_RCVLOWAT` なし）の回は 2.05 GB/s だった
- echo（`octets`）はサーバーの側も写さなくなるので 3 倍ほど
- 小さな呼び出し（ping・oneway・threads:4）は、ぶれ（10% ほど）の範囲で変わらない
- `Vec<u8>` のままでは、速さは変わらない。コピーが残るため

issue の終わりの条件の「実機の `get:1048576` で 10 GB/s」は、omniORBpy のサーバー相手の値で、段 10（#213）で実機で測る。

## 生成コードを使う側

```rust
// rustorb-idl -brust -Wbshared_octets Bench.idl
let data: rustorb_core::Octets = target.get_octets(1 << 20)?; // コピーなし
let bytes: &[u8] = &data;                                       // Deref
let owned: Vec<u8> = data.into_vec();                           // ほかに共有がなければコピーなし
target.put_octets(&rustorb_core::Octets::from(vec![0u8; 1 << 20]))?; // 写さずに送る
```

受け取った `Octets` は返事のメッセージ全体のバッファを持つので、小さな部分を長く持ち続けるなら `to_vec()` で写すとよい。
